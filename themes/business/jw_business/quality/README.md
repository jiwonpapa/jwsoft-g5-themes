# JW-Business 제작 품질 차단

2026-09-22 사용자 지시로 도입했습니다. 2026-09-23 사용자 지시로 메인 #5를 상품에서 제거했습니다. 현재 작성된 홈 4종·원페이지 3종·일반 페이지 16종, 총 23개 페이지는 예외 없이 재검토합니다. 기존 문서의 본문 구현 완료·개발 사이트 반영 기록은 디자인 품질 통과가 아닙니다. 현재 검사는 **실패가 정상**이며, 이 실패를 없애려고 나머지 규칙이나 검사 대상을 줄이면 안 됩니다.

## 필수 경로

저장소 루트에서 실행합니다.

| 명령 | 의미 |
| --- | --- |
| `bun run quality:check` | 현재 작성된 23종 및 이후 실제 작성된 페이지 자동 검사 |
| `bun run quality:release` | 홈 4종 + 원페이지 3종 + 일반 페이지 70종 전체 검사 |
| `bun run quality:start company-greeting` | 앞선 묶음 통과 및 대상 설계 준비 여부 확인 |
| `bun run quality:complete home` | 앞선 묶음 및 해당 4개 변형의 완료 조건 확인 |
| `bun run quality:prepare home 실제-구현-작업-ID` | 통과하지 않은 검토 초안 생성; 기존 파일 덮어쓰기 금지 |
| `bun run quality:compare home` | 검토 기록의 PC·모바일/라이트·다크 화면을 네 변형 비교판으로 생성 |
| `bun run quality:test` | 차단 장치의 통과·실패·우회 회귀 검사 |

루트 `check`, 테마 `check` 끝에 품질 검사가 필수입니다. 판매 ZIP 조립기는 JW-Business일 때 77종 전체 검사를 직접 실행합니다. `--gate`에 다른 자료를 주거나 품질 자료를 생략해도 이 호출은 생략되지 않습니다. `build`는 결함을 고치고 검토 화면을 준비할 수 있도록 실행 가능하며, 빌드 성공을 완료로 보고하지 않습니다.

자동 검사 workflow는 `.github/workflows/product-quality.yml`입니다. 원격에 반영된 뒤 실행됩니다. 이 작업에서 원격 branch protection·필수 상태 검사·관리자 우회 제한은 설정하지 않았습니다. 전체 저장소를 수정할 권한이 있는 구현자가 검사 코드까지 바꾸는 것을 로컬 스크립트만으로 막을 수는 없습니다.

## 1. 요구사항과 설계

`contract.json`은 77개 대상, 실제 경로, 목적, 구성 방식, 요구 콘텐츠, 필수 동작을 명시합니다. 현재 `ready: false`는 기존 결과를 승인하지 않았다는 뜻입니다. 기존 화면을 보고 거꾸로 `ready: true`만 쓰지 않습니다. 각 페이지의 첫 화면, 중간·마지막 흐름, 실제 사용할 자료를 구체화한 뒤 갱신합니다.

- 홈 #1의 히어로 슬라이더는 필수입니다. `data-jw-hero-slider`와 다음/이전/키보드/재생·정지/줄인 동작 설정의 PC·모바일 검증이 필요합니다.
- 디지털 상세 #2·사례 #4에는 실제 디지털 화면·결과 자료(`data-jw-digital-artifact`)가 필요합니다. 이 선택자 존재만으로 의미 적합성을 승인하지 않습니다.
- 선택자는 PHP 소스의 실제 마크업과 캡처 때의 실제 표시·수량을 모두 확인합니다. 주석이나 문구에 선택자를 넣는 것으로 통과할 수 없습니다.
- 이미 작성됐던 페이지를 스캐폴드로 되돌려도 검사 범위에서 사라지지 않습니다.
- 문구·사진·순서만 바꾼 동일한 태그/클래스 구성은 차단합니다. 한 목적의 5개 변형에서 3개 이상 도입 구조가 같은 경우도 차단합니다. 클래스 이름을 달리한 유사 디자인은 시각 비교에서 판단합니다. 구조 차이가 곧 디자인 품질이라는 뜻은 아닙니다.

## 2. 사진

`assets.json`에 원본 경로, SHA-256, 원본 ID(`origin`), 사용 페이지(`owner`)를 등록합니다. 기존 메인용 원본 세 장은 홈 #1 소유로 등록했습니다. 다른 페이지에는 허용 예외가 없습니다.

- 모든 본문 래스터 이미지와 CSS 배경을 검사합니다. PHP의 기존 사진 helper도 추적합니다.
- 새 사진·일러스트·화면 자료는 목적에 맞게 준비하고 원본 기록을 먼저 등록합니다.
- 파일 이름을 바꾼 복사, 동일 원본 ID, 유사 이미지의 페이지 간 사용을 차단합니다.
- 한 페이지의 PHP 마크업에서 동일한 이미지 경로를 두 번 이상 사용하면 `PHOTO_REPEAT_WITHIN_PAGE`로 차단합니다. CSS 배경과 서로 다른 크롭의 시각적 반복은 별도 화면 검토로 확인합니다.
- 해상도·형식 변환본도 같은 원본 ID와 같은 소유 페이지로 등록합니다. 같은 페이지의 반응형 변환본은 허용합니다.
- 원격·동적 경로 등 원본을 확인할 수 없는 이미지는 조용히 건너뛰지 않고 실패시킵니다. 향후 표현 방식이 늘어나면 분석기와 회귀 검사를 함께 보완해야 합니다.
- 렌더링된 이미지 목록도 검토 기록에서 합쳐 검사합니다. CSS/JS/PHP 우회로 표시되는 추가 이미지도 등록·소유 검사를 받아야 합니다.
- 유사도 검사는 경고가 아닌 차단입니다. 오탐이면 화면·원본을 확인하고 검사 보정 및 회귀 근거를 남깁니다. 묻지마 예외 목록은 없습니다.

내용 해시·축소 픽셀·명암 패턴 검사는 파일명 변경과 일반적인 재압축을 잡습니다. 원본 ID는 크롭·색보정 파생본을 추적합니다. **원본 기록을 거짓 작성한 임의의 강한 크롭까지 알고리즘이 전부 검출한다고 보장하지 않습니다.** 실제 이미지 적합성·중복 검토가 별도로 필수인 이유입니다.

## 3. 실제 화면과 독립 검토

구현 에이전트가 Codex 내장 브라우저에서 `g5themes.test`를 직접 열고 전체 화면을 수집합니다. 형님에게 스크린샷 수집을 떠넘기지 않습니다. 먼저 최종 소스의 빌드·개발 화면 반영 상태를 확인합니다. 개발 사이트 반영 권한은 별도 사용자 지시 범위에 따릅니다.

검토자는 구현과 다른 작업 식별자를 사용하고, 가능하면 독립된 검토 작업에서 비교합니다. 모든 페이지를 PC 1280–1920px와 모바일 360–430px, 라이트·다크로 확인합니다. 일반 페이지 묶음 5종은 **20개 전체 화면과 10쌍 비교 판단**, 메인 묶음 4종은 **16개 전체 화면과 6쌍 비교 판단**, 원페이지 묶음 3종은 **12개 전체 화면과 3쌍 비교 판단**이 필요합니다. 비교판 전체와 각 원본 화면의 첫 화면·중간·끝을 직접 봅니다.

검토 기록은 `quality/reviews/<group>.json`, 실제 캡처는 `quality/evidence/`에 둡니다. 캡처와 기록은 함께 보관해야 재현 가능합니다. JSON 구조는 `scripts/quality/model.ts`의 `Review`와 strict schema를 따릅니다.

각 캡처는 다음을 기록합니다.

- 실제 파일의 SHA-256, 페이지, 주소, 캡처 시각
- viewport 폭·높이, 전체 문서 높이, `fullPage: true`
- 라이트/다크 상태, 실제 렌더링된 이미지의 원본 경로 목록
- 요구사항별 DOM 개수와 실제 표시 여부

각 페이지는 목적·사진/자료 적합성·구성에 대한 구체적인 판단을 남깁니다. 각 변형 쌍은 첫 화면, 콘텐츠의 시각적 표현, 중간 리듬과 마지막 행동에서 어떻게 다른 선택 이유를 주는지 기록합니다. 차이가 약하면 `fail`입니다. 필수 동작은 PC·모바일별 조작 순서와 서로 다른 전후 화면을 남깁니다.

비교판 생성은 승인이 아닙니다. `prepare`는 `pending`·실패 항목만 만들고 자동 통과 기능은 없습니다. 빈 JSON, 같은 구현자/검토자 ID, 누락된 비교, 재사용 캡처, 잘못된 주소/크기, 변경된 증거 파일은 실패합니다.

검토의 `inputDigest`는 소스·사진·스타일·스크립트·토큰·생성 파일·정책·검사 코드의 현재 내용과 일치해야 합니다. 먼저 빌드를 마친 뒤 초안을 만듭니다. 검토 이후 해당 입력이 하나라도 달라지면 이전 기록을 재사용할 수 없습니다. digest만 새로 써서 검토한 것처럼 만들지 않습니다.

독립 검토자의 실제 신원과 화면 판단의 진실성을 JSON만으로 인증할 수는 없습니다. 이 장치는 기계적으로 확인할 수 있는 누락·불일치를 차단하고 실제 검토를 요구합니다. 외부 승인 권한 분리는 저장소 보호 설정이 담당해야 합니다.

## 4. 다음 묶음과 판매 ZIP

`quality:complete <group>`가 성공하기 전에는 해당 묶음을 품질 완료로 기록하거나 다음 묶음을 진행하지 않습니다. 기존 완료 보고서도 새로운 품질 검사를 통과한 증거로 사용할 수 없습니다. 실패 항목을 고치고 다시 검토하는 것이 다음 작업입니다.

판매 ZIP의 일반 `--gate` 자료도 이제 실제 JSON 내용이 필요합니다.

```json
{
  "schemaVersion": 1,
  "gateId": "contract-check",
  "result": "pass",
  "sourceCommit": "검사한 40자리 커밋",
  "inputDigest": "검사한 ZIP 입력의 64자리 SHA-256",
  "checkedAt": "실제 검사 ISO 시각"
}
```

`packageInputDigest(themeRoot)`로 계산한 실제 ZIP 입력과 자료가 일치해야 합니다. 단순 파일 존재, 실패 기록, 다른 커밋, 변경된 payload, 미래 시각으로는 ZIP을 만들 수 없습니다. 이 자료는 기존 구조·계약·설치 검사를 실제 수행한 후 발급하며, JW-Business의 실제 품질 검사 호출을 대체하지 않습니다.

## 검토 입력 범위 v2

새 `quality:prepare`는 schemaVersion 2의 묶음 digest를 생성합니다. 다른 묶음의 계약에 등록된 독립 PHP만 제외합니다. 미등록 파일·공용 PHP·CSS·JS·빌드 chunk·토큰·사진·정책·검사기는 보수적으로 모든 묶음에 포함합니다. 공유 변경은 관련 검토를 모두 무효화합니다. v1 기록은 기존 전체 digest로만 검증하며 자동 변환하지 않습니다. 기존 기록의 digest만 바꾸어 재승인하는 도구는 제공하지 않습니다. 사진 중복은 여전히 모든 페이지를 검사하고 출시 집계도 전체를 검사합니다. [브라우저 증거 수집](../../../../harness/ui/README.md)과 시각 승인은 별개입니다.
