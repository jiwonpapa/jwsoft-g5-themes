# JW-Business 전체 메뉴·페이지 개선 실행 기준

2026-09-23 · 대상: 개발 사이트의 상위 메뉴 7개, 하위 링크 전체, 메인 4종과 일반 페이지 70종. 메인 #5는 사용자 지시로 상품에서 제거했다. 현재 판매 가능 판정은 **불가**를 유지한다.

## 현재 화면에서 확인한 문제

- PC 회사소개 메뉴는 7개 주제 아래 35개 변형 링크를 한 번에 노출한다. 사업분야는 15개다. 사용자는 목적보다 레이아웃 번호와 기술 설명을 먼저 읽게 된다.
- [전체 메뉴 시야 점검](../reports/JW-BUSINESS-FULL-MENU-VISUAL-AUDIT-2026-09-23.md)에서 일반 페이지 70종 중 작성 16종, 안내 스캐폴드 54종이었다. 작성본도 같은 사진 세 장, 비슷한 제목·회색 구간·문의 마무리를 반복했다.
- 로컬 `quality:check`는 홈과 기존 작성 페이지의 디자인 준비, 사진 소유·재사용, 검토 증거 부족을 차단한다. 이 검사 결과를 경고로 바꾸거나 페이지를 검사에서 빼지 않는다.

## 메뉴 구현

G5 관리자 `get_menu_db()`를 메뉴의 단일 원본으로 유지한다. 상위 메뉴의 이름·순서·URL·PC/모바일 노출 설정을 변경하지 않는다. 변형 5개가 연속된 하위 메뉴만 테마가 주제별로 묶어 보여 준다.

PC 메가메뉴는 3열 주제 선택 화면이다. 현재 주제의 5개 변형만 가로로 펼치며, 다른 주제는 제목과 페이지 수만 보인다. 모바일은 기존 대분류→주제 구조에 페이지 수를 더하고, 한 주제씩 펼친다. 모든 하위 URL은 계속 접근 가능하다. 로컬 [메뉴 표시 시안](../../docs/prototypes/jw-business-menu-preview/index.php)은 실제 메뉴 PHP를 모의 G5 메뉴 데이터로 렌더링한다. 개발 사이트에는 아직 배포하지 않았다.

이 변경은 **메뉴를 읽는 방식**만 개선한다. 메뉴에서 보이는 `#1~#5`의 제목이 실제 화면과 맞는지 각 묶음 완료 때 재검증한다. 실제 페이지가 스캐폴드라면 메뉴 개선을 완성으로 보고하지 않는다.

## 페이지 제작 순서와 차단

1. **메인 4종과 원페이지 3종.** 메인 #1의 이미지 기반 시안과 실제 PHP의 간격을 닫고, #2~#4는 서로 다른 첫·중간·끝 구도를 제작한다. 원페이지 3종은 별도 자산 소유와 상품 포함 경계를 확인한다. 홈 네 변형을 PC·모바일/라이트·다크로 비교하고 `quality:complete home`까지 끝낸다.
2. **회사소개.** 기업개요 기존 5종의 사진·첫 화면 반복을 해결한다. 이어 인사말·비전·연혁·조직도·인증·오시는 길 6유형×5종을 스캐폴드 대신 실제 자료 중심 화면으로 제작한다. 해당 묶음 착수 전 `quality:start company-greeting`을 통과해야 한다.
3. **사업분야.** 사업 목록·사업 상세 각 5종의 중복 사진을 제거하고, 특히 디지털 상세·사례에는 읽을 수 있는 화면 결과물을 둔다. 프로세스 5종은 단계별 다른 산출물을 중심으로 만든다.
4. **프로젝트·채용·고객지원.** 프로젝트/게시판의 시연 자료와 빈 썸네일을 바로잡는다. 인재상·복리후생·고객센터 안내 각 5종을 페이지 목적에 맞게 작성한다.
5. **문의.** 연락처·문의 #2~#5를 완성하고 #1과 나란히 비교한다. 실제 G5 문의 기능과 안내 문구를 구분하며 제공하지 않는 예약·외부 연동을 암시하지 않는다.

## 한 묶음의 완료 조건

각 페이지는 **방문자의 질문 → 고유한 자료 → 다음 행동**을 먼저 한 장의 PC·모바일 시안으로 설계한다. 같은 유형의 5종은 사진·카드 순서만 다른 변형을 허용하지 않는다. 각각 다른 첫 화면, 대표 자료, 중간 리듬, 모바일 읽기 순서가 있어야 한다. 이미지는 원본·소유 페이지·파생본을 `quality/assets.json`에 등록하고 다른 페이지에 재사용하지 않는다.

소스 변경 뒤 구조·PHP·빌드 검사를 실행하고, 실제 G5 PC·모바일과 라이트·다크를 내장 브라우저에서 확인한다. 홈은 20개 전체 화면·10쌍 비교, 일반 페이지도 같은 묶음별 비교 근거를 남긴다. 품질 차단 통과와 실제 화면 검토가 끝나기 전에는 다음 묶음·판매 ZIP을 완료로 기록하지 않는다. 개발 사이트 반영과 소스 빌드는 별개로 보고한다.
