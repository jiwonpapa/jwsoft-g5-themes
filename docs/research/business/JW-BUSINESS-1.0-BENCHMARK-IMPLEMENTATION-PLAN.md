# JW-Business 1.0 벤치마킹 및 구현 방안

- 문서 상태: 구현 전 기준안
- 조사일: 2026-09-20
- 대상: 그누보드5 기업·사업체용 유료 테마
- 상품 방향: 기존 판매중단 상품 페이지를 새 이름·새 소스의 `JW-Business 1.0`으로 교체
- 구현 원칙: 최신 공식 G5 `theme/basic` 전체를 새 테마명 폴더로 복제해 시작하고, 기존 B2·B3와 G7 경험은 항목별 검토 후 선별 적용

2026-09-21 후속 결정: [출시 구현 범위](../../plans/JW-BUSINESS-1.0-IMPLEMENTATION-SCOPE.md)에서 75개 페이지·게시판 6개·최신글 8개 표현형을 확정했다. 아래 후보 수량·`inquiry`/`recruit` 스킨 제안·선택 효과와 차이가 있으면 확정 범위를 우선한다. 대표 PHP는 사용자 지시에 따라 8.3이며, 다른 지원 버전은 호환 검증 대상이다.

## 1. 결론

기존 B2·B3 소스를 Tailwind CSS로 기계 변환하는 방식은 채택하지 않는다. Bootstrap과 jQuery 플러그인, 중복 스킨, 여러 헤더·슬라이더 변형, 소스맵과 벤더 파일이 깊게 얽혀 있어 변환 비용에 비해 품질과 유지보수성이 나쁘다.

구현안은 다음과 같다.

1. **공식 최신 G5 `theme/basic` 전체를 `theme/jw_business`로 복제·개명하고 그 안에서 신규 소스를 작성한다.**
2. **B2·B3에서 검증된 사이트 구성과 스킨 범위만 가져온다.** 회사소개, 사업영역, 포트폴리오, 연혁, 조직도, 오시는 길, 문의, 게시판·최신글 구성은 유지한다.
3. **공통 시각 체계를 유지하면서 메인과 각 하위 일반 페이지에 레이아웃 4~5종을 제공한다.** 기업개요·인사말·연혁 각각이 4~5종이며 서로 다른 하위 메뉴를 묶어 회사소개 5종으로 세지 않는다. 같은 목적의 페이지에서 섹션·레이아웃을 다르게 하고 색상·서체·버튼·아이콘·공통 기능은 재사용한다.
4. **Tailwind CSS 4 + daisyUI 5 + TypeScript + Vite + Swiper를 개발 스택으로 사용한다.** 개발 package manager는 공통 표준에 따라 Bun으로 통일하며 고객에게는 빌드된 CSS·JS만 제공한다.
5. **관리자 페이지 빌더와 사이트 생성기는 만들지 않는다.** 기존 G5 메뉴·내용관리·게시판을 활용하고, 로고·색상·이미지·문구 변경 위치를 문서 한 장으로 명확하게 제공한다.
6. **기존 판매중단 상품 페이지를 `JW-Business 1.0`으로 교체하되 구형 소스와 자동 호환되는 덮어쓰기 업데이트로 취급하지 않는다.** 구형 판매본과 새 설치본을 분리하고 이전 가이드를 제공한다.

이 구조가 기존 판매 이력을 활용하면서도 구형 기술 부채를 다시 가져오지 않는 최적안이다.

## 3. 자체 제작 B2·B3 분석

아래 3.1~3.4는 앞선 소스 조사 기록이다. 2026-09-21에는 [기존 상품의 PC·모바일 화면을 Edge에서 별도로 직접 검토](ASKTHEME-B3-VISUAL-REFERENCE-2026-09-21.md)했다. 이번 화면 검토에서 소스 수량을 재검사하지 않았으며, 판매 설명의 제공 수량과 소스의 파일·변형 수량은 구분한다.

### 3.1 자산 규모

| 항목 | B2 | B3 | 판단 |
|---|---:|---:|---|
| 전체 파일 | 약 358개 | 약 2,718개 | B3는 벤더·SCSS·소스맵까지 포함되어 상품 소스가 비대함 |
| PHP | 약 116개 | 약 200개 | 다양한 페이지·스킨 자산은 재사용 가치가 있음 |
| CSS | 약 51개 | 약 268개 | 페이지별·플러그인별 스타일이 분산됨 |
| SCSS | 거의 없음 | 약 305개 | 고객 배포물에 개발 원본과 벤더 원본이 과도하게 포함됨 |
| JS | 약 28개 | 약 569개 | 중복 플러그인과 레거시 의존성이 큼 |
| 소스맵 | 소수 | 약 237개 | 판매 패키지에는 불필요함 |

### 3.2 B2의 특성

- 흰색 헤더와 별도 검정 유틸리티 바를 사용한다.
- 중앙 메뉴, 건물 이미지 히어로, 하단에 겹쳐 올라오는 3개 퀵 카드 구조다.
- 기업 사이트라는 용도는 명확하지만 헤더 층이 많고, 히어로가 화면을 주도하지 못한다.
- 카드가 히어로와 다음 섹션을 연결하는 방식은 당시에는 효과적이었지만 현재는 흔하고 공간을 잘게 나눈다.

**가져올 것**

- 기업 소개 → 사업영역 → 실적 → 문의로 이어지는 익숙한 정보 흐름
- 빠르게 이해되는 기업형 메뉴 명칭
- 사용 목적이 분명한 퀵 링크 개념

**버릴 것**

- 유틸리티 바와 주 메뉴를 별도 줄로 쌓는 구조
- 히어로 위에 여러 카드를 얹는 기본 구성
- 고정 폭·구형 타이포그래피·작은 화면에서 밀도가 높아지는 배치

### 3.3 B3의 특성

B3는 기존 자산 중 기능 범위가 가장 넓다.

- 헤더 6종: default, fulldown, gray, morph, pure, white
- 메인 레이아웃 8종: 기본, classic, classic2, community, foundation, mobile, onepage, portfolio
- 슬라이더 4종 이상: 일반, fade, onepage, portfolio
- 기업 페이지: 인사말, 회사소개, 사업·서비스, 연혁, 조직도, 오시는 길, 문의
- 게시판: basic, gallery, portfolio, webzine, youtube
- 최신글: basic, gallery, portfolio, slider, tab, video, webzine, youtube 계열
- 실제 건축 이미지 위에 큰 `CREATIVE DESIGN` 문구와 CTA를 둔 풀 비주얼 히어로

기능 목록은 우수하지만 판매 패키지 안에 Bootstrap 4, jQuery 계열, Tether, Popper, Noty, Swiper·Owl, Velocity, Stellar, YTPlayer, 여러 모바일 메뉴가 함께 존재한다. PHP 템플릿에도 Bootstrap 클래스가 광범위하게 결합되어 있다.

**가져올 것**

- 풀 화면 기업 비주얼과 강한 문구
- 기업 사이트에 필요한 실제 페이지·게시판 범위
- G5 메뉴, 내용관리, 게시판을 조합해 완성된 사이트를 제공한 경험
- 포트폴리오·웹진·갤러리·동영상처럼 실무에서 자주 쓰이는 표현 방식
- 연혁, 조직도, 지도, 문의처럼 기업 고객이 반복 요청하는 구성

**새로 구현할 것**

- 헤더와 메뉴 전체
- 히어로 슬라이더와 영상 처리
- 레이아웃 그리드와 모든 컴포넌트 스타일
- 게시판·최신글의 HTML 구조와 반응형 규칙
- 접근성, 모션 감소, 성능 최적화
- 자산 빌드·패키징·버전 관리

**이관하지 않을 것**

- 구형 6개 헤더, 8개 메인, 4개 슬라이더의 설정·구현을 그대로 이관하는 구조. 새로운 완성 페이지 변형 제공은 별도 기획
- Bootstrap 클래스와 Bootstrap 전용 페이징·카테고리 마크업 변환기
- 테마 동작용 jQuery 코드
- Owl, Velocity, Stellar, YTPlayer, Tether, Noty 등 구형 플러그인
- PC·모바일 템플릿 중복
- 데모용 스타일 선택기와 페이지 빌더 성격의 설정
- 소스맵, 벤더 원본, 사용하지 않는 예제 파일

### 3.4 핵심 판단

B3는 새 테마의 **기능 요구사항 목록**으로는 가치가 높지만 **코드 기반**으로는 적합하지 않다. 구소스를 고치면 화면은 바뀌어도 구조적 복잡성은 남는다. 따라서 `JW-Business 1.0`은 B3의 기능 완성도를 목표로 하되 코드 한 줄씩 옮기지 않는 전면 재작성으로 진행한다.

### 3.5 상품 화면 직접 검토 보완 — 2026-09-21

기존 상품의 화면에서는 기본 목록·탭·썸네일과 요약·갤러리·혼합형·포트폴리오 등 최신글 표현, 일반·웹진·갤러리·포트폴리오·유튜브 게시판 목록이 확인됐다. 기업·커뮤니티·협회·원페이지는 이 표현들과 소개·사업·실적 섹션을 서로 다른 비중으로 조합한다. 모바일에서도 소개는 한 열, 사진 갤러리는 두 열로 정보 성격에 맞게 배치한다.

**대표 디자인 하나는 콘텐츠 표현까지 한 종류로 줄인다는 뜻이 아니다.** 공통 색상·서체·버튼 규칙 아래 목적별 목록과 섹션을 구성하는 원리를 참고한다. 구형 디자인을 복제하거나 과거 스킨 수량 전체를 신규 범위로 자동 승계하지 않는다.

실제 데모 도메인은 DNS 오류로 접속되지 않았다. 위 내용은 상품 이미지의 육안 관찰이며 현재 실행·반응형·글쓰기 등의 검증 결과가 아니다. 원본 이미지와 변경이력에서 얻은 검증 항목은 [직접 검토 기록](ASKTHEME-B3-VISUAL-REFERENCE-2026-09-21.md)에 구분해 정리했다.

### 4.2 시장에서 확인되는 구매 요인

1. **메인 화면 한 장보다 설치 후 완성 가능한 전체 범위가 중요하다.** 상위 상품은 게시판, 최신글, 내용 페이지, 메뉴 연동과 설명서를 반복해서 강조한다.
2. **오래 판매되는 상품은 G5 버전 대응과 설치 설명이 분명하다.** 디자인이 최신이 아니어도 구매자가 예상 가능한 상품이 살아남는다.
3. **현재 가격대는 대부분 7만~10만원과 1도메인 라이선스다.** 무제한 라이선스의 높은 가격은 디자인 한 장이 아니라 반복 납품 시간 절감으로 설명해야 한다.
4. **설정 기능이 많다는 사실이 품질을 보장하지 않는다.** 헤더·메인 변형을 늘리면 데모는 풍부해 보이지만 각 조합의 모바일·접근성·G5 호환 검수 비용이 급증한다.
5. **AI로 평범한 랜딩 화면 생성은 쉬워졌다.** 상품의 방어력은 G5 연결, 완성된 서브페이지, 일관된 스킨, 설치·변경 문서, 실제 브라우저 검수에서 나온다.

### 4.3 `JW-Business 1.0`의 차별점

- 최신 기업 사이트 수준의 첫 화면
- G5에 실제 연결된 전체 사이트 구조
- 불필요한 관리자 빌더가 없는 단순한 설치·업데이트
- 고객 서버에 Bun·Node.js나 빌드 도구가 필요 없는 완성 자산
- 에이전시·제작자가 반복 사용할 수 있는 무제한 라이선스 후보
- `CHANGE-MAP` 한 장에서 로고, 색상, 이미지, 메뉴, 연락처, 지도, 게시판 연결 위치를 확인
- 오류·보안·업데이트 회귀에 집중한 명확한 기술 지원 범위

### 4.4 해외 상위 상품의 페이지 다양성 — 2026-09-21 보완

[해외 상위 WordPress 테마 조사](WORDPRESS-TOP-SELLERS-PAGE-VARIANTS-2026-09-21.md)에서 The7의 동일 데모 내 회사소개 4종·연락처 7종, Bridge의 메인·회사소개 변형, Avada·Betheme·Salient의 사이트 간 페이지 구성 차이를 확인했다. 기존의 단일 메인·일반 페이지 총 10개만 제공하는 방향은 분류별 선택권이 부족하다.

JW의 요구사항은 각 하위 일반 페이지마다 완성 레이아웃 4~5종과 재사용 섹션을 제공하는 것이다. 기업개요·인사말·연혁을 하나씩 만든 것은 회사소개 패턴 3종이 아니다. 이 집계 기준은 사용자 요구이며 해외 상품의 모든 하위 페이지가 각각 5종임을 입증했다는 뜻은 아니다. 색상·사진만 바꾼 페이지를 변형으로 세지 않으며 페이지가 많다는 이유로 빌더·폼 처리기·관리자 설정을 추가하지 않는다.

## 7. 디자인 방향

실제 구현 전 아래 세 방향의 장단점을 검토하되, 1차 승인안은 다섯 대표 화면을 하나의 시스템으로 제작해 색상·간격·서체뿐 아니라 G5 기능 화면의 일관성까지 확인한다. 여러 방향을 상품 설정으로 모두 넣지는 않는다.

### A. Editorial Tech — 권장

- 흑연색과 밝은 미네랄 배경을 기본으로 전기청색 한 색을 강조색으로 사용
- 실제 사람·공간·프로젝트 사진을 화면 가장자리까지 크게 배치
- 왼쪽 정렬 대형 문장과 숫자, 얇은 구분선
- 제조, IT, 건설, 연구, B2B 서비스에 폭넓게 적용 가능

### B. Architectural Minimal

- 아이보리, 차콜, 저채도 적색
- 이미지 수를 줄이고 공간·타이포그래피를 더 크게 사용
- 컨설팅, 건축, 법률, 회계, 전문 서비스에 적합

### C. Human Momentum

- 딥 네이비, 청록 한 색, 자연스러운 인물·현장 이미지
- 신뢰와 협업을 강조하는 콘텐츠 흐름
- 교육, 서비스, 조직·협회, 인재 중심 기업에 적합

### 7.1 권장 시각 명제

> 짙은 흑연색 프레임과 실제 현장 이미지를 크게 사용하고, 흰 여백과 한 가지 청색으로 기업의 신뢰와 속도를 표현한다.

### 7.2 콘텐츠 명제

> 첫 화면에서 무엇을 하는 회사인지 말하고, 사업영역과 실적으로 증명한 뒤, 소식과 문의로 연결한다.

### 7.3 상호작용 명제

> 스크롤 방향에 반응하는 헤더, 필요한 순간에만 움직이는 히어로와 사업영역 전환으로 깊이를 만들고, 읽기를 방해하는 장식 모션은 사용하지 않는다.

## 8. 디자인 시스템 초안

최종 값은 추가 시안까지 비교해 방향을 승인한 뒤 잠근다. 2차 시안은 후보이며 구현 기준으로 확정되지 않았다.

### 8.1 색상

색상의 단일 원본은 daisyUI 5의 semantic theme token이다. 라이트는 `corporate`, 다크는 `business`를 기준으로 하고 다음 역할만 사용한다.

| 역할 | daisyUI token |
|---|---|
| 페이지·박스 배경 | `base-100`, `base-200`, `base-300` |
| 기본 글자 | `base-content` |
| 주요 행동·포커스 | `primary`, `primary-content` |
| 보조 정보 | `secondary`, `secondary-content` |
| 제한된 강조 | `accent`, `accent-content` |
| 상태 | `info`, `success`, `warning`, `error`와 각 content token |

임의 HEX 팔레트와 라이트 전용 고정색을 컴포넌트에 넣지 않는다. 필요한 약한 면과 구분선은 현재 semantic color의 `color-mix()`로 만든다.

라이트·다크 전환은 1차 출시 필수 범위다. 메인만 색을 바꾸는 것이 아니라 일반 페이지, 게시판 목록·본문·댓글·쓰기, 로그인·가입·회원 기능, 검색·FAQ·1:1 문의와 테마가 담당하는 팝업까지 모두 같은 상태를 따른다. 사용자 선택이 없으면 시스템 설정을 따르고 명시적 선택은 브라우저에 저장한다. 이미지 오버레이, 표, 에디터 출력, CAPTCHA와 G5 공용 UI도 두 상태에서 검사한다. G5 코어 관리자 전체 화면은 테마 전환 범위에서 제외한다.

### 8.2 타이포그래피

- 한글·영문 공통: 공식 `Pretendard Variable 1.3.9` 다이내믹 서브셋 자체 호스팅, 디자인 토큰은 400·500·600·700
- 시스템 대체: `Pretendard, -apple-system, BlinkMacSystemFont, system-ui, sans-serif`
- 본문: 16~18px, 줄높이 1.65~1.75
- 내비게이션: 15~16px, 600
- 메인 제목: `clamp(3rem, 7vw, 6.5rem)`, 600~700
- 섹션 제목: `clamp(2.25rem, 4vw, 4.5rem)`, 600
- 숫자·영문에 별도 장식 폰트를 추가하지 않는다.

### 8.3 레이아웃

- 최대 화면 폭: 1,440px
- 기본 콘텐츠 폭: 1,280px
- 긴 본문 폭: 720px
- 데스크톱 12열, 태블릿 8열, 모바일 4열
- 좌우 여백: 모바일 20px, 태블릿 32px, 데스크톱 48~80px
- 섹션 간격: 데스크톱 112~160px, 모바일 72~96px
- 버튼 높이: 48px 기본, 56px 주요 CTA
- 큰 이미지에는 모서리 둥글기를 남용하지 않고 0~8px만 사용
- 배지와 상태 표시 외에는 알약형 UI를 사용하지 않는다.

### 8.4 컴포넌트 원칙

- 카드 격자는 사업 목록이나 소식 목록처럼 실제 반복 데이터에만 사용한다.
- 소개·실적·가치는 큰 이미지, 분할 레이아웃, 번호 목록, 수치 밴드로 표현한다.
- 그림자보다 경계선, 여백, 배경 명도 차이로 계층을 만든다.
- 아이콘은 Lucide SVG 한 종류로 통일한다.

## 9. 전체 사이트 메뉴 구조

기본 데모는 아래 전체 구조를 실제로 연결한다. 판매 설명에서 `메인 화면`만 보여주고 끝내지 않는다.

| 1차 메뉴 | 2차 메뉴 | G5 구현 |
|---|---|---|
| 회사소개 | 기업 개요, 인사말, 비전·가치, 연혁, 조직도, 인증·수상, 오시는 길 | 내용관리 또는 제공 PHP 템플릿 |
| 사업영역 | 사업 목록, 사업 상세 A, 사업 상세 B, 프로세스 | 내용 페이지 + 공통 상세 템플릿 |
| 포트폴리오 | 전체, 분야별 분류, 상세 | 갤러리형 게시판 |
| 미디어 | 공지사항, 뉴스·보도, 자료실, 영상 | basic·webzine·download·video 스킨 |
| 인재채용 | 인재상, 복리후생, 채용공고 | 내용 페이지 + 게시판 |
| 고객지원 | FAQ, 온라인 문의, 검색, 연락처 | FAQ + 문의 게시판 + G5 검색 |

푸터에는 개인정보처리방침, 이용약관, 이메일무단수집거부, 주소, 대표 연락처, 사업자 정보와 주요 링크를 둔다.

### 9.1 메가 메뉴

- 1차 메뉴 5~6개, 각 2차 메뉴 최대 7개
- 전체 폭 패널이 헤더 아래로 열림
- 왼쪽에는 메뉴 제목과 한 줄 설명, 오른쪽에는 2차 링크를 2~3열로 배치
- 홍보 배너를 넣더라도 하나만 사용
- G5 메뉴관리의 1·2단 메뉴를 기본 데이터로 사용
- 3단 메뉴는 지원하지 않는다. 필요한 경우 해당 상세 페이지 내부 내비게이션으로 분리한다.

## 10. 메인 화면 구성

### 10.1 섹션 순서

1. **풀 화면 히어로** — 회사의 한 문장, 설명, CTA
2. **근거 수치 밴드** — 설립연도, 프로젝트, 고객사, 기술·인증 등 3~4개
3. **사업영역** — 이미지와 연결된 세로 또는 가로 아코디언
4. **대표 프로젝트** — 큰 사례 이미지와 문제·해결·결과 서술
5. **핵심 역량·프로세스** — 번호 목록과 선형 흐름
6. **기업 소식** — 뉴스·공지 최신글을 하나의 편집형 피드로 구성
7. **문의 CTA** — 배경 이미지 또는 강한 단색과 연락 경로
8. **푸터**

### 10.2 카드 남용 방지

- 메인에서 같은 크기의 작은 카드 3~4개를 매 섹션마다 반복하지 않는다.
- 사업영역은 선택한 항목의 큰 이미지가 바뀌는 방식으로 공간을 사용한다.
- 대표 프로젝트는 한 건을 크게 보여주고 다음 사례 링크를 제공한다.
- 소식은 첫 글을 크게, 나머지는 텍스트 목록으로 계층을 만든다.

|---|---|---|
| `top` | `scrollY < 24px` | 투명 배경, 히어로 대비용 흰 글자, 항상 표시 |
| `scrolled` | 24px 이상 | 반투명 또는 단색 배경, 글자색 전환, 1px 경계선 |
| `hidden` | 96px 이후 아래 방향 누적 16px 이상 | `translateY(-100%)`로 숨김 |
| `visible` | 위 방향 누적 12px 이상 | 즉시 다시 표시 |
| `locked` | 메가 메뉴·모바일 드로어·검색·헤더 내부 포커스 활성 | 방향과 무관하게 표시 |

### 11.3 구현 규칙

- `passive: true` 스크롤 리스너와 `requestAnimationFrame`을 사용한다.
- 매 이벤트에서 레이아웃 값을 반복 측정하지 않고 `scrollY`와 이전 위치만 비교한다.
- 헤더 높이는 바꾸지 않고 `transform`, 배경색, 경계선만 애니메이션한다.
- 스크롤 방향이 1~2px 바뀔 때 흔들리지 않도록 누적 거리 임계값을 둔다.
- 페이지 최상단, 키보드 포커스 진입, 메뉴 열림 상태에서는 항상 보인다.
- `prefers-reduced-motion: reduce`에서는 헤더를 숨기지 않고 고정 표시한다.
- 브라우저 뒤로 가기와 앵커 이동 후에도 현재 위치에 맞는 상태를 다시 계산한다.

### 11.4 데스크톱 메가 메뉴

- 포인터 진입 후 120ms에 열고, 이탈 후 180ms에 닫아 대각선 이동 오작동을 줄인다.
- 키보드는 Tab으로 진입하고 Enter·Space로 열며 Escape로 닫는다.
- 메뉴가 열리면 `aria-expanded`, `aria-controls`를 갱신한다.
- 배경 딤은 선택 사항이며 콘텐츠를 완전히 가리는 강한 블러는 사용하지 않는다.
- 메뉴가 열린 동안 헤더 자동 숨김을 잠근다.

### 11.5 모바일 메뉴

- 우측에서 들어오는 전체 높이 드로어
- 상단 로고, 닫기 버튼, 1차 아코디언, 문의 CTA, 기본 링크 순서
- 열릴 때 본문 스크롤을 잠그고 현재 스크롤 위치를 보존한다.
- 포커스를 드로어 안에 가두고 Escape로 닫으며 닫은 뒤 메뉴 버튼으로 포커스를 되돌린다.
- 메뉴 항목의 펼침 버튼과 페이지 링크를 분리해 터치 오작동을 줄인다.
- 터치 목표 크기는 최소 44×44px로 한다.

## 12. 히어로·슬라이드 상세 명세

### 12.1 화면 구조

- 홈 히어로 높이: `100svh`, 최소 720px 데스크톱, 620px 모바일
- 헤더가 히어로 위에 겹치므로 별도 상단 빈 공간을 만들지 않는다.
- 최대 3개 슬라이드
- 각 슬라이드 콘텐츠: 작은 분류 문구, 2~3줄 제목, 한 줄 설명, CTA 최대 2개
- 기본은 왼쪽 정렬이며 이미지의 여백 영역에 문구를 둔다.
- 텍스트 대비가 필요한 경우 검정 그라디언트 오버레이를 사용한다.

### 12.2 슬라이드 동작

- 자동 재생: 6.5초
- 전환 시간: 약 800ms
- 이미지 전환: 페이드 또는 제한된 크로스페이드
- 텍스트: 분류 → 제목 → 설명 → CTA 순으로 60~100ms 간격
- 이미지: `scale(1.02)`에서 `scale(1)`로 아주 약하게 이동
- 마우스 오버, 키보드 포커스, 브라우저 탭 비활성화 시 자동 재생 일시정지
- 스와이프, 이전·다음, 현재/전체 숫자, 진행 막대를 제공
- 자동 재생 끄기 버튼을 제공하거나 슬라이더 전체를 일시정지할 수 있어야 함
- `prefers-reduced-motion`에서는 자동 재생과 확대 모션을 끈다.

### 12.3 이미지 처리

- `<picture>`로 AVIF → WebP → JPG/PNG 순서의 대체 형식을 제공
- 데스크톱과 모바일의 초점이 다른 경우 별도 크롭 이미지를 제공
- 첫 슬라이드 이미지는 `fetchpriority="high"`와 명시적 width·height 사용
- 다음 슬라이드는 lazy load
- 첫 히어로 이미지 권장 예산: 데스크톱 350KB 이하, 모바일 180KB 이하
- 단순 장식 이미지는 비어 있는 `alt`, 의미 있는 이미지는 콘텐츠를 설명하는 `alt` 사용

### 12.4 영상 슬라이드

- 최대 한 개만 허용
- 자체 호스팅 MP4/WebM, `muted`, `playsinline`, 포스터 필수
- 모바일과 데이터 절약 환경에서는 포스터 이미지로 대체 가능
- 활성 슬라이드가 아니면 재생하지 않는다.
- YouTube 배경 영상 플러그인에 의존하지 않는다.
- 영상이 실패해도 문구와 CTA는 정상 노출되어야 한다.

### 12.5 서브페이지 히어로

- 슬라이더를 사용하지 않는다.
- 40~48vh 범위의 정적 이미지 또는 단색 배경
- 현재 1차 메뉴, 페이지 제목, 짧은 설명, breadcrumb만 제공

## 13. 모션과 상호작용

### 13.1 허용하는 모션

- 첫 화면 문구의 짧은 진입
- 히어로 이미지의 매우 약한 확대·복귀
- 스크롤 방향 헤더
- 사업영역 아코디언의 이미지·텍스트 전환
- 이미지가 뷰포트에 들어올 때의 짧은 마스크 또는 투명도 전환
- 버튼 화살표 4~6px 이동

### 13.2 사용하지 않는 모션

- 전체 페이지 부드러운 스크롤 강제
- 커서 추적 장식
- 스크롤을 가로채는 섹션 고정
- 매 요소가 아래에서 반복 등장하는 동일 애니메이션
- 과도한 패럴랙스
- 숫자 장식만을 위한 장시간 카운터
- 배경 동영상 자동 재생을 여러 구간에서 반복

### 13.3 구현 수단

- Motion `inView()`와 `scroll()`
- `IntersectionObserver`는 애니메이션 외 가시성 판단에만 직접 사용
- `ResizeObserver`
- CSS transition·keyframes
- 상태 제어는 작은 TypeScript 모듈

GSAP, Lenis, ScrollMagic, Velocity, Stellar는 기본 의존성에 넣지 않는다.

## 14. 기술 스택

공통 버전·prefix·라이선스·Bun 명령은 [G5 테마 공통 플랫폼 표준](../../standards/G5-THEME-PLATFORM-STANDARD.md)을 상위 기준으로 사용한다. 이 절에는 비즈니스 테마의 사용 범위만 기록한다.

### 14.1 런타임과 개발 도구

| 영역 | 선택 | 적용 원칙 |
|---|---|---|
| CMS | 그누보드5 최신 5.6 계열 기준 | 코어 무수정, 메뉴·내용·게시판 API 사용 |
| 서버 | PHP | 8.3~8.5 검수, 기준 환경 8.4 |
| 스타일 | [Tailwind CSS 4](https://tailwindcss.com/docs/installation/using-vite) | 유틸리티와 CSS 변수 기반 토큰, 정적 CSS 출력 |
| UI 컴포넌트 | [daisyUI 5](https://daisyui.com/docs/v5/) | 폼·버튼·드로어·모달 등 기반 요소에 제한 사용 |
| 스크립트 | TypeScript | 프레임워크 없이 작은 모듈로 분리 |
| 번들러 | [Vite](https://vite.dev/guide/build) | 고정 파일명으로 빌드한 CSS·JS를 상품에 포함 |
| 슬라이더 | [Swiper](https://swiperjs.com/swiper-api) | Hero에 A11y·Autoplay·Navigation·Pagination 모듈만 사용 |
| 스크롤 효과 | [Motion](https://motion.dev/docs/scroll) | `inView()`·`scroll()`만 import, reduced motion에서 정적 표시 |
| 갤러리 | [PhotoSwipe](https://photoswipe.com/getting-started/) | 포트폴리오 상세에서만 동적 import, 원본 링크 fallback |
| 아이콘 | Lucide | 필요한 SVG만 번들 또는 인라인 |
| 이미지 빌드 | Sharp 개발 의존성 | AVIF·WebP·포스터 생성, 결과물만 배포 |
| package manager | [Bun](https://bun.sh/docs/pm/workspaces) 1.4.2 | 루트 workspace·catalog·`bun.lock`, 고객 서버에는 불필요 |
| 검사 | ESLint, Prettier, Stylelint, PHP lint, Playwright | 코드·실제 화면 검증에 사용 |

Tailwind 4의 기본 브라우저 기준에 맞춰 Chrome/Chromium 111+, Firefox 128+, Safari 16.4+를 기본 지원선으로 잡는다. 더 낮은 브라우저 지원이 필요하면 출시 전에 별도 CSS 빌드 전략을 결정한다.

### 14.2 프레임워크를 넣지 않는 이유

React, Vue, Svelte는 이 테마의 핵심 문제를 해결하지 않는다. G5가 서버에서 페이지를 렌더링하므로 메뉴, 슬라이드, 드로어, 탭, 아코디언 정도는 작은 TypeScript 모듈이 더 단순하다. 별도 앱 런타임을 넣으면 초기 JS와 고객 수정 난이도만 높아진다.

> 2026-09-21 변경: 아래 초기 판단은 [공개 영역 레거시 감사](../../reports/JW-BUSINESS-LEGACY-AUDIT-2026-09-21.md)와 [현대화 실행 계획](../../plans/JW-BUSINESS-LEGACY-MODERNIZATION-PLAN.md)으로 대체한다. JW-Business 공개 기본 번들의 최종 목표는 jQuery와 Migrate 0개다.

G5 코어가 사용하는 jQuery는 그대로 둘 수 있지만 새 테마 컴포넌트는 jQuery에 의존하지 않는다.

### 14.3 daisyUI 사용 범위

**사용**

- 버튼, 입력, textarea, checkbox, radio, select
- alert, modal, drawer의 기본 상태·접근성 스타일
- pagination, badge처럼 구조가 단순한 요소

**직접 설계**

- 헤더와 메가 메뉴
- 히어로
- 사업영역 아코디언
- 포트폴리오·뉴스 편집 레이아웃
- 서브 히어로와 푸터
- G5 게시판 목록·본문의 정보 계층

daisyUI 클래스를 그대로 늘어놓아 데모 같은 인상을 만들지 않는다. 브랜드 토큰을 연결하고 실제 디자인 시안에 맞춰 컴포넌트 표현을 제한한다.

### 14.4 의존성 규칙

- 루트 `bun.lock`을 커밋하고 catalog에서 정확한 버전을 고정한다.
- 쓰지 않는 플러그인을 예비용으로 넣지 않는다.
- 하나의 역할에 하나의 라이브러리만 사용한다.
- 운영 패키지에는 `node_modules`, 개발 소스맵, 예제 벤더 파일을 넣지 않는다.
- 외부 CDN에 필수 CSS·JS를 의존하지 않는다.

## 15. G5 통합 설계

### 15.1 기본 원칙

- G5 코어 파일은 수정하지 않는다.
- DB 테이블을 추가하지 않는다.
- 메뉴는 G5 메뉴관리 데이터를 사용한다.
- 회사 기본 내용은 내용관리 또는 제공한 PHP 템플릿 중 하나로 명확히 구분한다.
- 포트폴리오·뉴스·자료실·채용·문의는 게시판으로 구성한다.
- 하나의 반응형 마크업을 사용하고 별도 모바일 테마를 중복 유지하지 않는다.
- 검색, 새글, 로그인, 회원가입, 마이페이지, FAQ, 문의, 팝업 등 기본 화면도 동일 디자인 체계로 맞춘다.

### 15.2 권장 게시판 구성

| ID 예시 | 용도 | 스킨 |
|---|---|---|
| `portfolio` | 수행 사례·제품 | portfolio |
| `news` | 회사 뉴스·보도 | webzine |
| `notice` | 공지 | basic |
| `download` | 카탈로그·자료 | download |
| `video` | 영상 자료 | video |
| `recruit` | 채용 공고 | recruit/basic |
| `inquiry` | 온라인 문의 | inquiry |

게시판 ID는 예시이며 테마 코드에서 특정 ID를 하드코딩하지 않는다. 데모 설치 안내에서 사용자가 연결할 위치를 설명한다.

### 15.3 자산 로딩

- `add_stylesheet()`와 `add_javascript()`를 사용한다.
- 빌드 결과 파일명은 `theme.css`, `theme.js`처럼 안정적으로 유지한다.
- 테마 버전 문자열을 query parameter로 붙여 캐시를 갱신한다.
- 전역 JS 변수는 하나의 namespace 아래에 제한한다.
- 스크립트가 실패해도 메뉴 링크, 본문, 폼 제출은 기본 동작해야 한다.

### 15.4 콘텐츠 편집 방식

관리자 빌더 대신 다음 세 층으로 나눈다.

1. **G5 관리자**: 메뉴, 게시판, 내용, 팝업, 회원·문의 관리
2. **명확한 PHP partial**: 홈 섹션 문구와 연결을 수정
3. **CSS 변수와 이미지 폴더**: 색상, 로고, 대표 이미지 교체

고객 지원에서 반복되는 질문을 줄이기 위해 `docs/CHANGE-MAP.md`에 다음을 표로 제공한다.

- 로고 파일 경로와 권장 크기
- 브랜드 색상 변수 6~7개
- 히어로 이미지·영상 경로와 크롭 규칙
- 메인 문구와 CTA 위치
- 메뉴와 게시판 연결 방법
- 회사 정보·SNS·지도·푸터 위치
- 캐시 삭제와 자산 버전 갱신 방법

## 17. 기존 판매중단 상품 교체 방식

### 17.1 상품 운영

- 기존 판매중단 상품 페이지의 상품번호와 판매 이력은 유지하고 제목·파일·대표 이미지·설명·데모를 `JW-Business 1.0` 기준으로 교체한다.
- 신규 상품번호는 만들지 않는다.
- `완전 신규 소스`, `구형 판매본에 덮어쓰는 업데이트 아님`을 상품 설명 상단에 표시한다.
- 기존 구매자가 판매처 권한에 따라 새 파일을 내려받을 수 있음을 운영 결정에 포함한다. 라이선스·업데이트·지원 기간의 적용 기준일은 기존 판매 조건과 판매처 규정을 확인해 명시한다.
- 정상 판매가는 390,000원이며 출시일부터 1개월은 상품의 실제 판매가격을 290,000원으로 변경한다. 판매자 부담 쿠폰은 사용하지 않고 종료일에 390,000원으로 복원한다.

### 17.2 기술적 이전

- 구형 판매본 파일 위에 `JW-Business 1.0`을 덮어쓰지 않는다.
- 별도 테마 폴더명으로 설치한다.
- DB의 게시판 글과 메뉴 데이터는 유지할 수 있지만 스킨 지정과 내용 페이지 마크업은 다시 연결한다.
- 이전 문서에는 `유지 가능`, `재연결 필요`, `수동 이관`을 구분한다.

| 항목 | 처리 |
|---|---|
| 회원·게시글·첨부파일 | 유지 가능, DB 변경 없음 |
| 메뉴 데이터 | 유지 가능, 2단 구조 확인 필요 |
| 게시판 스킨 | `JW-Business 1.0` 스킨으로 다시 지정 |
| 로고·대표 이미지 | 새 규격으로 교체 |
| 구형 메인 문구 | 새 partial에 수동 반영 |
| 구형 커스텀 CSS·JS | 자동 이관하지 않음, 개별 검토 |
| 구형 헤더·슬라이더 설정 | 폐기, `JW-Business 1.0` 단일 구조 사용 |

## 18. 데모 콘텐츠와 이미지 정책

### 18.1 데모 업종

첫 데모는 **업종 중립적인 프로젝트 기반 기업**으로 잡는다. 사람·공간·프로젝트 결과를 함께 보여 주어 기술·건설·설계·전문 서비스·제품 기업에 치환할 수 있어야 한다. 판매 상위 기록은 테마의 범용성과 G5 화면 제공 범위를 뒷받침하지만 특정 제조 이미지의 우월성을 증명하지 않으므로 첨단 제조·산업 기업으로 고정하지 않는다.

### 18.2 필수 데모 데이터

- 실제 회사처럼 연결되는 회사명·슬로건·사업설명
- 사업영역 3~4개와 서로 다른 상세 내용
- 대표 프로젝트 6개 이상
- 뉴스·공지·자료실 각 5개 이상
- 연혁 8~12개 항목
- 인증·수상 6개 이상
- 조직도, 지도, 문의 폼, 채용공고
- 모든 글의 목록·상세·검색·빈 상태·페이지 이동 데이터

무작위 lorem ipsum이나 같은 문장을 복제하지 않는다. 데모 문구와 이미지의 관계를 검수해 구매자가 설치 직후 전체 구조를 이해하게 한다.

### 18.3 이미지 방향

- 실제 공간감이 있는 공장, 연구소, 설비, 팀 협업, 결과물 사진
- 과도하게 푸른 AI 기업 이미지, 유리 구체, 떠 있는 3D 아이콘은 피한다.
- 한 페이지 안에서 사진의 색온도와 대비를 통일한다.
- 모든 배포 이미지의 상업 이용·재배포 조건을 확인하고 출처 목록을 보관한다.

### 20.5 사무실 Ubuntu 오프라인 검증 환경

아래 장비 정보는 2026-09-20의 이전 읽기 전용 조사 기록이며 현재 상태를 보장하지 않는다. 형님의 명시적 지시 전에는 SSH 접속, 설정, 배포, G5·DB·Docker 생성과 시험을 수행하지 않는다. 지시를 받으면 공개 데모 서버보다 기존 사무실 Ubuntu 환경을 먼저 재확인한다.

2026-09-20 확인 기준 장비 상태는 다음과 같다.

| 항목 | 확인값 |
|---|---|
| SSH 별칭 | `localubuntu` |
| 호스트명 | `stagingserver` |
| 운영체제 | Ubuntu 24.04 x86_64 |
| CPU·메모리 | 16 CPU, 62GiB RAM |
| 디스크 | 466GB 중 약 157GB 여유 |
| 웹 서버 | Nginx 1.30.1 실행 중 |
| PHP | PHP 8.4.21 CLI, curl·gd·intl·mbstring·mysqli·pdo_mysql·zip 확인 |
| 컨테이너 | Docker 29.1.3 실행 중 |
| 데이터베이스 | MariaDB 10.3·10.11 컨테이너가 내부 포트로 실행 중 |
| Bun·Node.js | 미설치 |

Bun·Node.js가 없는 상태는 고객 runtime 검증 장비라는 역할에 맞는다. Tailwind·daisyUI·TypeScript·Vite 빌드는 개발 환경에서 Bun을 우선 사용하고, Ubuntu runtime 장비에는 빌드된 테마와 G5 실행 파일만 배치한다. 별도의 재현 build worker에는 고정 Bun 버전을 설치하며, 공통 플랫폼의 compatibility gate가 요구할 때만 Node 24 LTS를 개발 도구 runtime으로 추가한다.

```text
개발 Mac
  ├─ 테마 PHP·CSS·TypeScript 작성
  ├─ Bun + Vite production build
  ├─ 정적 검사와 판매 ZIP 생성
  └─ rsync/SSH로 검증본 전송
           ↓ 내부망
사무실 Ubuntu
  ├─ Nginx + PHP 8.4
  ├─ 테마별 독립 G5 검증 인스턴스
  ├─ 테마별 독립 DB 또는 초기화 가능한 검증 DB
  └─ PC·모바일 실제 브라우저 검수
```

운영 원칙은 다음과 같다.

- 외부 도메인, TLS, CDN, 공개 포트는 초기 개발에 사용하지 않는다.
- 현재 실행 중인 다른 서비스와 데이터베이스를 임의로 변경하지 않는다.
- 테마별 G5 디렉터리와 DB를 분리해 메뉴·게시판·샘플 데이터가 섞이지 않게 한다.
- 개발 소스를 서버에서 빌드하지 않고 `package/theme/<slug>` 결과만 동기화한다.
- 내부 접속 주소는 상품 문서에 기록하지 않고 개발 환경 문서에서만 관리한다.
- 영카트 미사용, 비로그인·로그인·관리자, 모바일·PC 상태를 내부 서버에서 실제로 확인한다.
- 판매 전 공개 데모가 필요해지는 시점에 검증된 동일 ZIP을 별도 서버로 올린다.

명시적 구현·검증 지시가 내려오면 첫 검증 후보를 `business/jw-business` 하나로 제한한다. 이 환경이 재현된 뒤에만 병원 테마 검증 방식을 별도로 결정한다.

| daisyUI 느낌이 그대로 남음 | 기초 폼·상태에만 사용하고 핵심 화면은 토큰 기반 직접 설계 |
| 히어로가 무겁고 느림 | 3장 제한, 이미지 예산, 첫 장 우선 로딩, 영상 한 장 제한 |
| 스크롤 헤더가 사용을 방해함 | 거리 임계값, 메뉴·포커스 잠금, reduced-motion 상시 표시 |
| 최신 화면만 만들고 G5 하위 화면이 방치됨 | 회원·검색·FAQ·게시판 상태를 출시 게이트에 포함 |

| 고객 수정 문의가 반복됨 | 변경 위치 문서, 권장 이미지 규격, 게시판 연결표를 패키지에 포함 |
| AI 생성 테마와 차이가 약함 | 실제 G5 전체 흐름, 전문 데모 데이터, 성능·접근성 검수로 차별화 |

## 23. 최종 구현 판단

`JW-Business 1.0`은 **구소스 개선판이 아니라 기존 상품의 경험을 반영한 신규 제품 소스**로 만든다. B2·B3에서 가져올 것은 메뉴와 페이지 범위, 게시판 경험, 기업 사이트에 필요한 기능 목록이다. Bootstrap 기반 마크업, 여러 변형, 구형 플러그인과 중복 파일은 가져오지 않는다.

시각적으로는 `Editorial Tech` 방향을 우선 추천한다. 풀 화면 실제 현장 이미지, 왼쪽 정렬 대형 문장, 한 가지 청색, 넓은 여백으로 범용 기업 테마이면서도 AI가 빠르게 만든 카드형 랜딩과 구분할 수 있다. 기술적으로는 Tailwind CSS 4와 daisyUI 5를 개발 기반으로 사용하되, 상품의 얼굴인 헤더·히어로·사업영역·포트폴리오는 직접 설계한다.

첫 구현은 **추가 시안 제작 → 후보 비교 → 다섯 대표 화면 방향 승인 → 라이트·다크 토큰 잠금 → 모바일 보정 → G5 골격 구현** 순서로 시작한다. 디자인을 승인하기 전에 테마 PHP와 전체 스킨을 만들지 않는다.
